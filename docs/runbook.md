# Tether Operations & Incident Response Runbook

This document details standard operating procedures, failure recovery playbooks, and troubleshooting steps for the Tether distributed monitoring platform.

---

## 1. System Components & Health Probes

| Component | Role | Health / Diagnostics Probe |
|---|---|---|
| **FastAPI API** | REST API & Ingress | `GET /health/live`, `GET /health/ready`, `GET /health` |
| **Prometheus Exporter** | Application & Runtime Metrics | `GET /metrics` |
| **PostgreSQL 16** | Durable source-of-truth storage | `pg_isready -U netwatch -d netwatch` |
| **Redis 7** | Celery broker, results, distributed locks | `redis-cli ping` |
| **Celery Workers** | Probe execution & alert dispatch | `GET /api/workers` / `celery inspect ping` |
| **Celery Beat** | Periodic target scheduler (single instance) | Periodic job log inspection |
| **Nginx Ingress** | Reverse proxy, HTTP routing & rate limiting | `nginx -t` & HTTP 200 on `/health/live` |

## 2. Incident Playbooks

### Playbook 1: API Service Unavailable (HTTP 502 / 503 / 504)

#### Symptoms
- Dashboard reports "Network Error" or 502 Bad Gateway.
- Reverse proxy unable to connect to upstream backend (`backend:8000`).

#### Diagnostic Steps
1. Verify container status:
   ```bash
   docker compose ps backend
   ```
2. Check FastAPI liveness and readiness probes (via ingress or local port):
   ```bash
   curl -i http://localhost/health/live
   curl -i http://localhost/health/ready
   ```
3. Inspect backend structured JSON logs:
   ```bash
   docker compose logs --tail=100 -f backend
   ```

#### Recovery Actions
- **Database unreachable**: If `/health/ready` reports `"database": "unhealthy"`, check PostgreSQL container and connection pool limits (`DB_POOL_SIZE`, `DB_MAX_OVERFLOW`).
- **Memory exhaustion / OOM**: Increase container memory ceiling in `docker-compose.prod.yml`.
- **Restart backend container**:
   ```bash
   docker compose restart backend
   ```

---

### Playbook 2: Celery Workers Offline or Stale

#### Symptoms
- Target checks are queued but remain in `PENDING` or `QUEUED` state.
- `GET /api/workers` lists 0 active worker nodes or stale heartbeats.

#### Diagnostic Steps
1. Verify Celery worker processes:
   ```bash
   docker compose ps celery-worker
   ```
2. Check worker logs:
   ```bash
   docker compose logs --tail=100 -f celery-worker
   ```
3. Inspect Redis broker queue depth:
   ```bash
   docker compose exec redis redis-cli llen monitoring
   ```

#### Recovery Actions
1. Verify Redis connectivity:
   ```bash
   docker compose exec redis redis-cli ping
   ```
2. Scale or restart workers:
   ```bash
   docker compose up -d --scale celery-worker=4
   ```
3. Clean stuck locks in Redis if necessary:
   ```bash
   docker compose exec redis redis-cli keys "lock:target:*"
   ```

---

### Playbook 3: Monitoring Checks Not Executing (Celery Beat Down)

#### Symptoms
- `next_check_at` timestamps for targets are in the past, but no new jobs are being enqueued.

#### Diagnostic Steps
1. Verify that **exactly one** Celery Beat instance is running:
   ```bash
   docker compose ps celery-beat
   ```
2. Inspect Beat logs:
   ```bash
   docker compose logs --tail=100 -f celery-beat
   ```

#### Recovery Actions
- **Never run multiple Beat processes**: Ensure only 1 scheduler replica is active to prevent duplicate job storms.
- Restart Celery Beat:
   ```bash
   docker compose restart celery-beat
   ```

---

### Playbook 4: Alerts & Notifications Not Delivered

#### Symptoms
- Outages occur (target is DOWN) but no emails, Slack messages, or Webhooks arrive.

#### Diagnostic Steps
1. Check `GET /api/alerts` to verify whether `AlertEvent` was generated by the state machine.
2. Inspect `NotificationDelivery` attempts and error logs:
   ```bash
   curl -H "Authorization: Bearer <TOKEN>" http://localhost/api/alerts/<ALERT_ID>
   ```
3. Verify worker logs for `deliver_alert_event` task errors:
   ```bash
   docker compose logs celery-worker | grep AlertTask
   ```

#### Recovery Actions
- **SMTP credentials invalid**: Update SMTP password/port in `/notifications` and use the "Test Channel" action.
- **Slack webhook expired**: Re-generate Incoming Webhook URL in Slack and update channel configuration.
- **SSRF Block**: Verify webhook destination does not resolve to loopback (127.0.0.1) or private RFC1918 addresses if prohibited.

## 3. Database Maintenance & Backup Procedures

### PostgreSQL Backup Procedure
Execute a consistent online snapshot of the Tether database:
```bash
docker compose exec postgres pg_dump -U netwatch -F c -b -v -f /tmp/tether_backup.dump netwatch
docker compose cp postgres:/tmp/tether_backup.dump ./tether_backup_$(date +%Y%m%d_%H%M%S).dump
```

### PostgreSQL Restore Procedure
```bash
# 1. Terminate active application connections
docker compose stop backend celery-worker celery-beat

# 2. Restore database schema and data
docker compose cp ./tether_backup.dump postgres:/tmp/tether_backup.dump
docker compose exec postgres pg_restore -U netwatch -d netwatch -v -c /tmp/tether_backup.dump

# 3. Restart application stack
docker compose start backend celery-worker celery-beat
```

## 4. Database Migrations Workflow (Alembic)

### 1. Generating a New Migration
```bash
cd backend
alembic revision --autogenerate -m "describe_schema_change"
```

### 2. Reviewing Migrations
Always inspect the generated script in `backend/alembic/versions/` to verify foreign keys, indexes, and constraints before applying.

### 3. Applying Migrations in Production
```bash
cd backend
alembic upgrade head
```

### 4. Migration Rollback Strategy
```bash
# Revert the most recent migration
alembic downgrade -1

# Revert to a specific revision ID
alembic downgrade <REVISION_ID>
```

## 5. Data Retention & Table Cleanup

Tether automatically purges aged monitoring telemetry via the `app.tasks.maintenance.cleanup_old_data` periodic Celery task:
- `RESULT_RETENTION_DAYS` (default: 30 days)
- `JOB_RETENTION_DAYS` (default: 14 days)
- `ALERT_RETENTION_DAYS` (default: 90 days)
- `AUDIT_LOG_RETENTION_DAYS` (default: 365 days)

To trigger maintenance cleanup on demand:
```bash
docker compose exec celery-worker python -c "from app.tasks.maintenance import cleanup_old_data; print(cleanup_old_data())"
```
